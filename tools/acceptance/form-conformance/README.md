# form-conformance

اختبار مطابقة مشترك لراسم النماذج الديناميكية على الويب وiOS وأندرويد والخادم، من مخطط واحد: `contracts/schemas/upload-form.json`. مبدأ المنصة: **نتيجة التحقق متطابقة على الواجهات الثلاث** (صف «الحقول المتغيرة» في اختبارات القبول).

- `forms/main.json`: نموذج يغطي أنواع الحقول العشرة الممكنة في v0 (دون `location` وحقول `sensitive`) وقواعد التحقق والشروط ونوع المادة. يُفحص بمخطط `upload-form.json` في كل تشغيل.
- `cases.json`: 57 حالة (صالح / غير صالح / شرطي). كل حالة: النموذج، نوع المادة، القيم المُدخلة، والنتيجة المتوقعة `{valid, errors:[{field, code}]}`. التوقعات مكتوبة يدويًا لا مولَّدة من أي تنفيذ.
- `reference.mjs`: تنفيذ مرجعي يثبت اتساق الحالات؛ **لا يُعتمد عليه حكمًا**. الحَكَم هو `cases.json`.

## كيف تستهلكها كل واجهة

1. اقرأ `cases.json` (وملفات النماذج التي يشير إليها `forms`) كما هي، دون نسخها إلى مستودع الواجهة.
2. شغّل مدقّقك الأصلي على كل حالة وأنتج `{"platform": "web|ios|android", "results": {"<case id>": {"valid": bool, "errors": [{"field", "code"}]}}}`.
3. `node tools/acceptance/form-conformance/run.mjs --compare=web.json,ios.json,android.json` يقارن كل ملف بالتوقعات (ومنها ببعضها). أو يمرّرها `scripts/dynamic-fields.mjs --platforms=…` إلى مقياس القبول.

## الدلالات (تعريفات هذا الاختبار)

هذه القواعد مشتقة من أوصاف `upload-form.json`، وما لم يحسمه المخطط حُسم هنا ويلزم أن يؤكده مالك العقد (ملاحظة في الطلب):

| القاعدة | الحسم |
| --- | --- |
| الرؤية | الحقل مرئي إن طابق `material_types` نوعَ المادة (أو لم يحدده) **و**تحقق `condition` من قيمة حقل مرئي آخر. `equals` على `multi_select` يعني «يحتوي». الحقل الذي يعتمد على حقل مخفي مخفي. |
| المخفي | يُتجاهل بقيمته: لا خطأ ولا فحص، حتى لو كانت القيمة خاطئة النوع. |
| الفراغ | `undefined` أو `null` أو `""` أو مصفوفة فارغة. الفارغ المطلوب ← `required` (لا قاعدة غيره)؛ الفارغ الاختياري يتخطى كل القواعد. `false` قيمة موجودة. |
| الطول | بنقاط الترميز (code points) لا وحدات UTF-16 ولا مجموعات الحروف: الإيموجي خارج BMP = 1، وكل علامة تشكيل = 1. هذا الفخ الأشهر بين JS وSwift وKotlin. |
| التشذيب | لا يُشذَّب شيء في التحقق؛ المسافات محتوى. |
| `pattern` | ECMA-262 بعلم unicode، يُطابق في أي موضع ما لم يُثبَّت بـ `^…$`. |
| `min`/`max`/`not_before`/`not_after`/`min_items`/`max_items`/`max_size_bytes` | حدود شاملة؛ التاريخ يُقارن لحظةً زمنية بغض النظر عن الإزاحة، ويجب أن يكون date-time كاملًا (RFC 3339). |
| المرفق | القيمة المجردة المتحقَّق منها: مصفوفة `{mime, size_bytes}` للملفات المختارة. `accept` يدعم `type/*`. (الشكل النهائي لقيمة المرفق في `dynamic_fields` من اختصاص العقد.) |
| الأخطاء | خطأ واحد لكل حقل (أول قاعدة تفشل بالترتيب: required، type، ثم قواعد النوع)، ومرتبة بترتيب الحقول في النموذج. رموز المفردات: `required type min_length max_length pattern min max option min_items max_items not_before not_after accept max_size_bytes`. |

## ما لا يغطيه

نشر إصدار جديد مع بقاء سجلات القديم مقروءة وإكمال مسودات الهاتف القديمة أمران من الخادم؛ يُضافان إلى `dynamic-fields` حين يوجد الخادم. حتى ذلك الحين تبقى نتيجة `dynamic-fields` جزئية.
