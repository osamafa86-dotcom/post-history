# اختبار حمل compose

المهمة 3 من #352؛ اختبار القبول رقم 4 `concurrent-load`. يستعمل autocannon لعدم توفر k6 محليًا، وعميل tus المشترك للقطع الحقيقي للاتصال والاستئناف من HEAD. لا هوك مُحاكى.

ثبّت `npm ci --prefix tools/acceptance` ثم `npm ci --prefix tools/load`. شغّل خدمات compose المحلية والعامل وoutbox على قاعدة قابلة للإزالة. جهّز حسابات اصطناعية بالأداة `tools/acceptance/field-trial/rehearsal-accounts.mjs`، وسجّل دخول الأدوار المطلوبة للحصول على رموز مؤقتة في البيئة فقط. لا تحفظ كلمات المرور أو الرموز في ملفات.

مرّر `LOAD_LOCAL_ONLY=1` و`LOAD_API_URL` و`LOAD_TUS_URL` و`LOAD_TOKENS` (JSON بمفاتيح reporter وproducer وbuyer_admin)، ولقياس الذاكرة مرّر أيضًا `LOAD_CONTAINERS` (أسماء حاويات compose مفصولة بفواصل). ثم:

```sh
node tools/load/run.mjs
```

المدة الافتراضية 60 ثانية، تضبط بـ`LOAD_DURATION_S` بين 10 و600. السكربت يضيف 50 مادة وجلسة رفع. يولّد ملفًا اصطناعيًا مؤقتًا حجمه 50,000,000 بايت ويطلق 50 رفعًا معًا، ويقطع 13 منها مرة واحدة ثم يستأنف. ينفذ لاحقًا سيناريو API مستقلًا: 100 طلب/ث للوارد و100 للكتالوج، ويعدّ أخطاء HTTP والاتصال والمهلة ويكشف عدم بلوغ 95% من معدل الطلبات المستهدف. لا يسجّل أجسام الردود أو العناوين أو الحسابات.

`docker stats` يُقرأ دوريًا، والنتيجة تتضمن ذروة مجموع ذاكرة الحاويات المحددة وعدد العينات وأخطاء القراءة. تُكتب النتيجة عبر writeResult المشترك بعد تصديق مخطط measurement، باسم نطاق يطابق إعدادات التشغيل (افتراضيًا 50x50mb-api200rps) وبلا استبدال ملف سابق. يُذكر طور التوقف في notes إن تعذّر اكتمال السيناريو. تُحفظ في `docs/measurements/api/`، مع p50/p95/p99 للمدد المقيسة. خطأ التهيئة لا يولّد نتيجة مختلقة. عند طلب LOAD_MEMORY=docker صراحةً يمنع غياب الأداة أو daemon بدء التشغيل.

تبقى النتيجة `partial` حتى دون أخطاء: هذا حجم #352، أما الخطة فتطلب 60 رفعًا × 2 GB وعدم تدهور الإشعارات والقرص المؤقت. لا تقيس هذه الأداة القرص أو زمن الإشعار أو تطابق البصمة بعد معالجة الخادم؛ استعمل اختبار القبول الأصلي لهذه الجوانب. لا توسّع إذن التشغيل إلى خدمات حقيقية.

التحقق المحلي: اختبارات النسب المئوية وتحويل الذاكرة وحارس العناوين، وautocannon ضد خادم HTTP مؤقت للتأكد من رصد 403 ومدد الردود. **لم يُنفّذ حمل compose هنا.**

## تشغيل بلا Docker لقياس الأجزاء المتاحة

بموافقة المنسق في #358، `LOAD_MEMORY=skip` يلغي استدعاءات docker stats واشتراط أسماء الحاويات. يسمح بمكدس خدمات محلي حقيقي مبني من المصدر أيضًا؛ الحارس المحلي وLOAD_LOCAL_ONLY يبقيان إلزاميين. تُكتب حقول docker_memory الثلاثة بقيمة `unverified` صراحة، ولا تُستبدل بأصفار؛ تبقى النتيجة partial حتى عند نجاح الرفع والـAPI. اذكر في القياس أن البيئة ليست compose. الافتراضي يفحص توفر docker stats للحاويات المحددة: إن تعذّرت القراءة أو لم تُحدّد حاويات، يستعمل skip ويعلن الذاكرة unverified. اطلب LOAD_MEMORY=docker لفرض القراءة والفشل قبل القياس عند غيابها. تبقى أسماء الحاويات غير الصالحة خطأ تهيئة؛ لا يجري قياس ذاكرة المضيف بديلًا عن ذاكرة الحاويات.


## حمل مخفّض للتكليف 6

للتشغيل الفعلي على compose المحلي، بعد تجهيز الحسابات والخدمات كما سبق:

```sh
LOAD_UPLOAD_COUNT=5 LOAD_FILE_MB=100 LOAD_API_RPS=20 LOAD_DURATION_S=10 node tools/load/run.mjs
```

هذه خمس جلسات متزامنة، لكل منها 100,000,000 بايت، مع قطع واستئناف جلستين (تقريب ربع العدد للأعلى). المعدل المستهدف هنا 20 طلبًا/ث مجموعًا بين المسارين، ولا يُنسب إليه قياس 200 طلب/ث. حدود القيم: عدد الرفع 1–50، وحجم الملف 1–100 MB عشرية، ومعدل API زوجي 2–200. يظل الافتراضي 50 × 50 MB و200 طلب/ث دون هذه المتغيرات.

يأخذ اسم ملف القياس وdevice.model النطاق المطلوب، مثل 5x100mb-api20rps؛ وتفصل المقاييس upload_target_count وupload_prepared وupload_completed بين المطلوب والمُحضّر والمكتمل فعلًا. النتيجة partial عند اكتمال السيناريو المحدود بلا أخطاء، وfail عند الإخفاق، ولا تمثل معيار الخطة الكامل.
