# مقترح بدء بناء الكود وفريق الوكلاء — منصة المكتبة المرئية

19 أكتوبر 2026 · يُقرأ مع «خطة تنفيذ منصة المكتبة المرئية — النسخة الثالثة»

الهدف من هذه الوثيقة: تحويل مرحلة التأسيس في الخطة (الأسابيع 1–6) إلى عمل برمجي يبدأ غدًا، بمستودع واحد، وعقود مكتوبة قبل الكود، وفريق وكلاء يعمل كل وكيل منهم في حزمة يملكها، وبشر يقومون بما لا يستطيعه الوكلاء.

## 1. المبادئ الحاكمة للبناء

1. **العقود قبل الكود.** تُكتب أولًا مواصفة OpenAPI 3.1 للواجهة، ومخططات JSON Schema للنماذج الديناميكية، ومخطط الخط الزمني JSON، ومخطط أحداث Outbox. كل وكيل يبني ضد العقد لا ضد كود وكيل آخر.
2. **لا نبني ما لم تثبته الخطة بعد.** في التأسيس لا متجر ولا دفتر أستاذ ولا محرر؛ فقط ما يُنتج أرقامًا للقرارات 3 و6 و7 و8 و14 و15 و17 من ملحق القرارات.
3. **اختبار القبول يُكتب قبل الميزة.** كل تذكرة تحمل معيار القبول من قسم «اختبارات القبول» في الخطة، ويُحوَّل إلى سكربت قابل للتكرار.
4. **القياس مخرج أول.** كل نموذج أولي يكتب نتائجه ملفات JSON تحت `docs/measurements/`، فتكون مراجعة البوابة مبنية على بيانات لا انطباعات.
5. **الأسرار والحسابات باسم الشبكة** منذ اليوم الأول، وخارج المستودع.

## 2. هيكل المستودع (monorepo)

```
palpost-library/
  docs/
    plan/                 نسخة الخطة المعتمدة + سجل القرارات (ADR لكل بند في الملحق)
    measurements/         نتائج النماذج الأولية بصيغة JSON
  contracts/
    openapi.yaml          واجهة /v1: الهوية، المواد، جلسات الرفع، الأحداث، التنبيهات
    schemas/              material, upload-form (JSON Schema subset), timeline, outbox-event
  apps/
    api/                  NestJS: خادم بوحدات (identity, materials, uploads, workflow, notifications)
    web/                  Next.js: الوارد الحي، راسم النماذج، لوحة الإنتاج، منصة اختبار المشغل
    ios/                  SwiftUI: نموذج الرفع (tus خلفي + مسار IETF) والنسخة الخفيفة والقياس
    android/              Compose: نموذج الرفع (UIDT + خدمة أمامية) وشاشة تهيئة المصنّعين والقياس
  workers/
    media/                Python: فحص الملف، SHA-256، النسخة الخفيفة، HLS، الصور، المحاذاة الصوتية
    ai/                   Python: بوابة التفريغ، المسار المحلي (Whisper GPU)، كشف اللقطات، الحصص
  infra/
    compose/              docker-compose للتطوير والاختبار: Postgres، tusd، MinIO محليًا، الطابور
    tusd/                 إعداد tusd لـ R2 بأجزاء متساوية، وعلم المسودة التجريبي لتجربة iOS
    terraform/            الحسابات والنطاقات والتخزين
  tools/
    netlab/               محاكي شبكة متقطعة + أداة قياس نافذة الاتصال وزمن الجزء
    asr-bench/            اختبار التفريغ المقارن: WER، خطأ الأسماء، نسبة الرفض، كلفة الدقيقة
    render-bench/         زمن تصدير القالب العاجل: طبقات Remotion + تركيب FFmpeg مقابل البدائل
  .github/workflows/      CI لكل حزمة، وفحص العقود، وفحص الأسرار
```

كل حزمة فيها ملف `CLAUDE.md` يصف اتفاقياتها (اللغة، التسمية، الاختبار، ما يُمنع) ليعمل أي وكيل فيها دون سياق المحادثة.

## 4. تعريف «منجز» لكل تذكرة

- الاختبارات تمر في CI، واختبار القبول المقابل موجود سكربتًا.
- لا أسرار في الكود؛ فحص الأسرار يمر.
- كل نص واجهة في ملفات موارد بالعربية والإنجليزية.
- كل قرار تقني يُسجَّل ADR في `docs/plan/decisions/`.
- نتائج القياس إن وُجدت محفوظة في `docs/measurements/` بصيغة متفق عليها.
- مراجعة من وكيل الجودة ووكيل الأمن قبل الدمج.

## 5. فريق الوكلاء

الوكيل هنا جلسة عمل مستقلة (Claude Code أو ما يماثله) لها تعليمات محددة، وفرع وworktree خاصان، وحزمة تملكها في المستودع. الوكلاء يكتبون الكود ويختبرونه؛ البشر يقررون ويدمجون ويجرون ما يحتاج هاتفًا حقيقيًا في غزة أو مالًا حقيقيًا.

### 5.3 بروتوكول التنسيق

1. **العقود مجمّدة لكل دورة أسبوعين؛** تغييرها يمر بـ PR على `contracts/` يوافق عليه المنسّق، وتُولَّد مكتبات العملاء آليًا بعده.
2. **فرع وworktree لكل تذكرة،** وPR واحد لكل تذكرة، مع اختباراته ومعيار قبوله.
3. **مراجعتان قبل الدمج:** الجودة (التغطية والقبول) والأمن (التهديدات والأسرار)؛ المنسّق يدمج.
4. **سجل القرارات واحد:** `docs/plan/decisions/` بصيغة ADR، ويُحدَّث ملحق القرارات في الخطة من هناك.
5. **القياس بصيغة واحدة:** كل أداة قياس تكتب JSON بالمخطط المتفق عليه في `contracts/schemas/measurement.json`.
6. **تقرير يومي قصير من المنسّق:** ما اكتمل، ما تعطّل، ما ينتظر قرارًا بشريًا.
7. **ملف `CLAUDE.md` في كل حزمة** هو الذاكرة المشتركة؛ ما لا يُكتب فيه لا يُفترض أن وكيلًا آخر يعرفه.

### 5.4 ما لا يستطيعه الوكلاء ويحتاج بشرًا

- تشغيل النماذج على هواتف فعلية في غزة والضفة وتسجيل نتائجها (المراسلون والمشرف الميداني).
- تجربة الصرف بمال حقيقي، والتواصل مع بوابات الدفع والبنوك، والامتثال.
- مقابلات المؤسسات المشترية وتثبيت مواصفات التسليم.
- امتلاك الحسابات والنطاقات والمفاتيح والشهادات، والموافقة على كل دمج يمس العقود أو الأمن.
- القرارات العشرة المطلوبة من الإدارة في الخطة.

## 6. أول يومين عمليًا

1. إنشاء المستودع بالهيكل أعلاه، وCI فارغ يمر، وملفات `CLAUDE.md` لكل حزمة.
2. كتابة `contracts/openapi.yaml` v0 لمسارات: الدخول، إنشاء مادة، جلسة رفع، اكتمال الرفع، حالة المادة، التنبيهات.
3. كتابة `contracts/schemas/upload-form.json` بالمجموعة الفرعية المسموحة من JSON Schema، ومخطط `measurement.json`.
4. `infra/compose` يشغّل Postgres وtusd وMinIO والطابور محليًا، مع إعداد tusd لـ R2 بأجزاء متساوية.
5. هيكل `tools/netlab` بسيناريو واحد (0.5 ميغابت/ث، فقد 30%، انقطاع كل دقيقتين) وأداة تسجّل نافذة الاتصال.

بعدها تنطلق تذاكر الأسبوعين 2–3 للوكلاء 2 و3 و4 و7 و8 بالتوازي.
