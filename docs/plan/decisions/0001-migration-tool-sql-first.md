# 0001 — أداة الترحيل: SQL خام يشغّله node-pg-migrate، وأنواع الخادم تُولَّد من قاعدة البيانات

- الحالة: مقبول
- التاريخ: 2026-10-19
- المسؤول: وكيل العقود والبيانات
- بند ملحق القرارات: — (يحسم سؤال «Prisma أم Drizzle» في `apps/api/CLAUDE.md`)

## السياق

المخطط في مرحلة التأسيس يعتمد على أشياء لا تعبّر عنها لغات مخططات ORM: قيد مؤجل بمحفّز لمجموع حصص المساهمين = 100، فهارس جزئية ومركبة بترتيب تنازلي، محفّز يسند رقم الإيصال ويمنع تغييره، سلسلة تجزئة لسجل التدقيق مع منع التحديث والحذف، وقيود `CHECK` على JSONB. وقاعدة المستودع: «العقود قبل الكود، لا نماذج بيانات يدوية». نحتاج أداة تشغّل هذه الترحيلات محليًا وفي CI بلا تهيئة، مع `down` يُختبر، وطريقة يحصل بها وكيل الخادم (NestJS) على أنواع آمنة دون كتابة المخطط مرتين.

## الخيارات

1. **Prisma Migrate + Prisma Client.** مخطط `schema.prisma` هو المصدر ويولّد SQL. لا يعبّر عن المحفّزات ولا القيود المؤجلة ولا الفهارس الجزئية ولا `CHECK` إلا بتعديل SQL المولَّد يدويًا، فيصير هناك مصدران. يحتاج محرّك ثنائي، و`prisma db pull` يُسقط القيود.
2. **Drizzle Kit (مخطط TypeScript يولّد SQL).** يدعم `CHECK` والفهارس الجزئية، لكن المحفّزات والقيود المؤجلة ترحيلات مخصصة يدوية؛ يبقى المصدر مزدوجًا (TS + SQL مخصص) ويتطلب حزمة في `apps/api` التي لا يملكها هذا الوكيل بعد.
3. **SQL خام يشغّله node-pg-migrate** (ملفات `.sql` بقسمي Up/Down، معاملة لكل ترحيل، جدول `schema_migrations`، يعمل بـ `npx` بلا تثبيت). الوصول من الخادم عبر **Drizzle** بمخطط يُولَّد من القاعدة بـ `drizzle-kit pull` بعد كل ترحيل.
4. **dbmate / Flyway.** SQL خام أيضًا، لكنهما خارج منظومة Node (ثنائي Go أو JVM) فيضيفان خطوة تثبيت في CI وفي أجهزة المطورين.

## القرار

الخيار 3: ملفات SQL في `apps/api/src/db/migrations/` هي الحقيقة الوحيدة للمخطط، يشغّلها `node-pg-migrate` عبر `apps/api/src/db/migrate.sh`، ووكيل الخادم يستعمل Drizzle بأنواع مستبطَنة من القاعدة لا مكتوبة يدويًا. اخترناه لأنه الوحيد الذي يعبّر عن كل قيد نحتاجه في مكان واحد، ويعمل في CI بالأمر نفسه الذي يعمل محليًا، ويبقي الأنواع تابعة للمخطط لا العكس.

## الدليل

`apps/api/src/db/scripts/check.sh` يمر محليًا وفي CI (مهمة `db`): ترحيل كامل صعودًا، اختبار دخاني يثبت كل قيد ومحفّز (`tests/smoke.sql`)، ثم `down` يفرغ المخطط من الجداول والدوال، ثم صعود ثانٍ واختبار ثانٍ. لا قياس أداء هنا لأن القرار ليس قرار أداء.

## التبعات

- أسهل: أي ميزة Postgres متاحة فورًا؛ مراجعة الترحيل = مراجعة SQL مقروء؛ لا محرّك ثنائي ولا خطوة توليد قبل التشغيل.
- أصعب: لا تحقق من الأنواع وقت الكتابة في الترحيل نفسه (يعوّضه الاختبار الدخاني والـ CI)؛ على وكيل الخادم إعادة `drizzle-kit pull` بعد كل ترحيل مدمج، ويُضاف فحص في CI يفشل إن اختلف المخطط المستبطَن عن الملف الملتزم (مهمة لوكيل الخادم عند إنشاء حزمة `apps/api`).
- يُراجع لاحقًا: إن تضخّم عدد الترحيلات اليدوية في المرحلة التجارية (التراخيص، دفتر الأستاذ)، يُعاد النظر في توليد الجزء الخالي من المحفّزات بـ Drizzle Kit مع بقاء SQL هو ما يُلتزم به.
